### 2026-11-11-23-10-00-a0840f s1 MEDIUM firstcall/core/read.py:343
Email headers are parsed outside the read budget, so one message can still hold the worker (denial of service). `_check_budget` runs only on the body (`_body_text`). `_read_email` first asks the `policy.default` parser for From and Subject, and the Subject is cut to MAX_LINE_CHARS only after it has been parsed whole. The stdlib parser is quadratic in a header's length: every token re-copies the rest of the value (`email/_header_value_parser.py` in CPython 3.12.12: `get_unstructured` 1129-1169 via `get_fws` `value.lstrip()` at 1052 and `_wsp_splitter(value, 1)` + `''.join(remainder)` at 1157/1169; `get_atext` `value = value[len(atext):]` at 1215 for address headers). A header of N whitespace-separated tokens costs about N copies of the remaining text. Estimate from that source, unverified by execution (no shell in this session): seconds to tens of seconds for a few hundred KB, about a minute at 1 MB, hours at the 10 MB intake cap. `jobs.keep_lease` renews the lease while `process` runs, so nothing times the read out. Harmed principal: the org; v0.1 runs one worker, so every lead behind that message waits and alerts go out late. Attacker: any stranger who can email the intake address (bounded by the upstream mail provider's header limit), or anyone posting to an email source directly. The module comment 'this budget bounds that input, so one message cannot hold a worker for long' is therefore not true of headers, and the cap-level tests in tests/test_pr1a_review.py only fill the body. Related, outside this slice: `store.delivery_key` parses Message-ID with the same policy inside the API request (firstcall/intake/store.py:28-29), and an invalid Message-ID falls back to `get_unstructured`.
Trigger: A stranger emails the org's intake address a message whose Subject (or From display name) is several hundred KB of folded, space-separated one-letter words. The provider's webhook posts it to /intake/inbox with valid source auth, intake returns 202, and the worker sits in `message.get("From")` / `message.get("Subject")` while the lease keeps renewing. Sent repeatedly within the 60-a-minute source allowance, the single worker never reaches real leads. Needs a mail path that accepts headers that large; a direct authenticated post can use the full 10 MB.
Suggestion: Bound the header block before any header is parsed: raise OverBudgetError when the raw header section (bytes before the first blank line) or any single header value is over a small cap (for example 64 KB in total, MAX_LINE_CHARS per unfolded value). Alternatively parse with `policy.compat32` and read From/Reply-To with `email.utils.getaddresses` and Subject as a truncated raw string, so no structured header parser sees unbounded text. Apply the same cap before the Message-ID parse in store.py. Add a CPU-limit test with a 1 MB Subject and a 1 MB From display name of single-letter words.
